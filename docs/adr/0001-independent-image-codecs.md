# ADR-0001: RGB・深度の画像コーデックをVRS保存処理から分離する

- 状態: 採用
- 日付: 2026-10-30
- 対象: `scripts/image_codecs.py`、`image_codec_builtin.py`、`image_codec_storage.py`、VRS入出力

## 背景と要求

RGBと深度は別々の方式で圧縮・復元する必要があります。RGBにJPEG、16bit深度にPNG、将来は深度専用方式を使用する場合でも、ROSbag変換処理やVRSライターの分岐を増やさずに追加できることを要求します。

圧縮器と復元器は同じPythonクラスである必要はありません。必要なのは、同じ保存データの契約を理解することです。また、画像圧縮と、VRSレコード全体のLZ4/Zstandard圧縮は異なる層です。

既存の未圧縮画像、IMU、設定情報、旧形式の読み出しは維持します。テスト用に実収録データを取得・公開しません。

## 決定

### Strategy + Interface Segregation

`ImageEncoder` と `ImageDecoder` を別々のProtocolにします。それぞれ `validate(ImageSpec)` と `encode(pixels, ImageSpec)` または `decode(bytes, ImageSpec)` を実装します。既存のPNG/JPEG実装は両方を実装しますが、圧縮側・復元側で異なるライブラリを使う拡張も可能です。

現段階の契約は、各フレームを独立に復元できる、入力を変更しない処理です。フレーム間予測、キーフレーム、辞書更新、動画コーデックの状態管理は対象外です。それらを導入するときは別のADRで、ランダムアクセスと状態の保存契約を定義します。

### Registry + Factory + Dependency Injection

`CodecRegistry` は `(name, version)` をキーに、圧縮器・復元器の生成関数を別々に登録します。`CodecSpec` の方式別設定から生成し、ライター／リーダーへ明示的に渡します。グローバルな可変登録表は使用せず、入出力オブジェクトは登録表の写しを保持します。

`CodecSpec.version` は本リポジトリのビット列・復元契約の版であり、OpenCVやJPEG規格の版番号ではありません。異なる実装でも同じキーを登録する限り、その契約に従う必要があります。既存キーの二重登録は拒否します。

ROSbag変換器にはコーデック処理を持たせません。既存の `writer_factory` を接続点とし、ライターの `image_codecs: Mapping[int, CodecSpec]` で論理ストリームごとに選択します。CLIもこの接続点を利用するため、変換器自体の変更は不要です。

ファイル中の名前をPythonのモジュール名として読み込んだり、依存パッケージを自動導入したりしません。未知の方式・未対応の版は明確なエラーです。圧縮バイト列だけの抽出は、対応する復元器がなくても可能です。

### Adapterで保存方法を隔離

コーデックはVRSを知りません。`image_codec_storage.py` が圧縮バイト列とVRSの間を接続します。

現行の固定依存 `vrs==1.2.2` の公式Python接続には、任意の画像ContentBlockを作成するAPIが公開されていません。`sample_with_image` はC++側で `ImageFormat::RAW` に固定されています。VRS本体がJPEG/PNGを表現できることと、公開Python APIからそのストリームを作れることを区別します。

そのため、現行の圧縮画像は公式 `sample` の文字列メタデータに明示的なBase64として格納します。JPEG/PNGデータをRAW画像として偽装しません。自作C++ライターや実行時の第三者モジュール書き換えは追加しません。

将来、公式APIから適切な `image/jpg`、`image/png`、独自形式のブロックを生成できるようになった時点で、新しい保存方式のAdapterを追加できます。圧縮・復元のStrategyやROSbag変換器は変更不要です。

## 保存契約と互換性

| 保存対象 | ストリームの保存版 | payload_encoding | 内容 |
|---|---:|---|---|
| 既存のRAW画像 | 2 | `native_image` | 本来の寸法と画素型の画像ブロック |
| 新しい圧縮画像 | 3 | `image_codec_base64_v1` | 圧縮バイト列のBase64を `some_string` に保存 |
| IMU・その他 | 2 | 既存値 | 変更なし |

圧縮画像には `image_codec_json` タグを保存します。記述子の版、方式名、契約の版、設定値、元の寸法・ROS画素形式・用途、可逆性を含めます。センサー設定の `config_json` は別に保持し、深度倍率などを画像圧縮設定と混同しません。

RAWだけのファイルは従来どおり保存版2です。圧縮画像を含むファイルのファイルタグは3とし、各ストリームは自身の版を保持します。読み出し時はストリームのタグを判定します。旧リーダーは新しい圧縮形式を拒否しますが、従来のRAW出力まで変更することはありません。

`read_data_records()` は復元した、行余白なし・正規化したバイト順の画素バイト列を返します。JPEGの場合は元画像との完全一致を意味しません。`read_encoded_image_records()` は圧縮バイト列と記述子を返し、両APIを混同しません。

## 精度と検証

- `raw`: 対応する全画素形式。float32のNaN、Inf、符号付きゼロを含むビット列を保持します。
- `png`: uint8/uint16を可逆保存します。float32を黙って整数化しません。
- `jpeg`: 8bitのRGB/BGR/単色に限定します。深度とアルファ付き画像は拒否します。
- 深度専用拡張: `lossless=True` の登録を要求します。非可逆深度には量子化、誤差上限、無効深度の意味などを定める別の契約が必要です。

入力の型・形状、出力の型・形状、Base64、PNG/JPEGの形式ヘッダーと寸法を検査します。復元後に8bit化や型変換で不一致を隠しません。標準の復元画像上限は256 MiBです。独自復元器にも割当量の検査を要求します。登録時の可逆性宣言だけで第三者実装の数学的な正しさを保証するものではありません。

品質判定は方式ごとに変えます。RAW/PNGは全画素・全ビット一致、JPEGは人工画像に対する平均絶対誤差を検査します。JPEGのテスト閾値を、任意の画像に対する精度保証とは扱いません。

## 採用しなかった案

1. ライター／リーダーに方式ごとのif文を増やす: 追加のたびに保存処理を変更し、圧縮と復元の対応が分散するため不採用です。
2. 圧縮器と復元器を必ず同一クラスにする: 別実装による復元や読み出し専用環境の構成を妨げるため要求しません。
3. JPEG/PNGをRAW画像ブロックへそのまま渡す: VRSの宣言と内容が矛盾するため不採用です。
4. C++を独自ビルドして画像形式を追加する: 公式Python配布物だけで動かす現行要件から外れ、配布・ビルド保守が増えるため今回は採用しません。
5. ファイルに書かれた実装名を動的にimportする: 未信頼ファイルからのコード実行を避けるため不採用です。

## 影響・制約

Base64には概ね4/3のサイズ増加と文字列化の費用があります。後段のレコード圧縮で必ず取り戻せるとは仮定しません。圧縮速度・ファイルサイズの優劣を保証する変更ではありません。

圧縮画像は標準のVRS画像ブロックではないため、汎用VRSビューアーの自動表示は保証しません。公式PyVRSでメタデータを取得し、対応する復元器で読むことはテストします。Aria固有スキーマへの適合も保証しません。

将来の深度専用方式は、実装と契約テストを登録する拡張点までを今回の対象とします。RVL等の特定アルゴリズムを本番用として実装したと主張するものではありません。

## 検証するテスト

- `tests/test_image_codecs.py`: 全画素、画素型、RGB/BGR/アルファ、設定検査、未知の方式・版、破損データ、独立した登録表。
- `tests/test_image_codec_e2e.py`: 640×480の人工ROS1 bag → 通常CLI → 実VRS → 公式PyVRS＋OpenCVによる独立復元。RGB3方式×深度2方式×レコード圧縮3方式。
- 同ファイルの深度拡張テスト: 圧縮器と復元器を別クラス・別登録表で実装し、本物のVRSにuint16/float32を保存・復元します。例の圧縮方式はテスト専用です。
- 既存回帰: 保存版2、旧形式、IMU、時刻・途中書き出しの検査を引き続き実行します。
